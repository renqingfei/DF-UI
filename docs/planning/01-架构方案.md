# 01 · 架构方案

> 状态：草案 · 待定稿
> 目标：一个仓库产出三套组件库（PC / H5 / uniapp），对外像三个独立产品，对内共享同一套地基。

---

## 一、核心矛盾与解法

### 矛盾

"既要 Element Plus 那样全能，又要能跑微信小程序" 这两件事天生冲突：

| 冲突点 | 网页端 | 小程序端 |
| --- | --- | --- |
| 渲染层 | 真实 DOM，可随时读写、测量 | 逻辑层与视图层分离，**没有 DOM**，测量要走异步接口 |
| 标签 | `div` / `span` / `input` | `view` / `text` / `input`（内置组件，行为固定） |
| 弹层 | `position: fixed` + Teleport 到 body | 无 Teleport；原生组件（`video`/`map`/`camera`）永远盖在最上层 |
| 富文本 | `v-html` 直接插 | 不支持，必须走 `rich-text` 组件 |
| 样式 | 全套 CSS | 选择器受限（无通配符、无部分伪类、无深层后代选择器） |
| 单位 | px / rem / vw | rpx（750 设计稿等分） |

**结论：界面层无法三端复用，强行复用只会三端都做不好。**

### 解法：分层复用

```
┌─────────────────────────────────────────────────────────┐
│  tokens   设计令牌：颜色 / 圆角 / 间距 / 字号 / 阴影 / 动效  │  100% 共享
├─────────────────────────────────────────────────────────┤
│  core     逻辑内核：校验规则、弹层栈、日期算法、状态钩子     │  ~90% 共享
│           约束：不许出现 document / window / DOM 操作       │
├─────────────────────────────────────────────────────────┤
│  API 契约  属性名、事件名、插槽名、默认值、类型定义          │  100% 对齐
├──────────────┬──────────────────┬───────────────────────┤
│  pc/ 界面层   │   h5/ 界面层      │   uni/ 界面层          │  各写各的
│  div + CSS   │   div + CSS      │   view + rpx          │
│  鼠标交互     │   触屏手势        │   小程序受限写法        │
└──────────────┴──────────────────┴───────────────────────┘
```

**实际工作量约 1.7 套，而非 3 套。** 其中 pc 与 h5 的界面层还能再共用约 60%（同为浏览器环境）。

## 二、分包职责

| 包 | 包名 | 职责 | 产物形态 |
| --- | --- | --- | --- |
| `packages/tokens` | `@df-ui/tokens` | 唯一颜色/尺寸真相源。一份 JSON 生成 CSS 变量、SCSS 变量、TS 常量三种产物 | JS + CSS + SCSS |
| `packages/core` | `@df-ui/core` | 与界面无关的逻辑：表单校验引擎、弹层层级管理、日期计算、剪贴板、防抖节流、组合式函数 | ESM + CJS + d.ts |
| `packages/icons` | `@df-ui/icons` | 图标源文件（SVG）与构建脚本，产出网页版组件 + 小程序版 base64/字体 | Vue 组件 + 静态资源 |
| `packages/pc` | `@df-ui/pc` | PC 后台组件库 | ESM + CJS + UMD + CSS + d.ts |
| `packages/h5` | `@df-ui/h5` | 移动端 H5 组件库 | ESM + CJS + CSS + d.ts |
| `packages/uni` | `@df-ui/uni` | uniapp 组件库 | **源码分发**（见下） |

### 为什么 uni 包必须"源码分发"

小程序不能运行预编译好的 Vue 运行时组件，`.vue` 源码必须交给 uni-app 自己的编译器处理成小程序页面结构。所以 `@df-ui/uni` **不打包**，直接发布 `.vue` 源码，并遵循 `uni_modules` 规范，配合 `easycom` 实现"写标签即自动引入"，用户无需手动 import。

## 三、组件 API 对齐原则

三端组件的**属性名、事件名、取值含义必须完全一致**，用户学一次三端通用。

```vue
<!-- PC 端 -->
<df-button type="primary" size="large" :loading="saving" @click="save">保存</df-button>

<!-- H5 端 -->
<df-button type="primary" size="large" :loading="saving" @click="save">保存</df-button>

<!-- uniapp 端 -->
<df-button type="primary" size="large" :loading="saving" @click="save">保存</df-button>
```

**允许的差异**（写进各端文档的"平台差异"小节）：

1. 某端不提供某个组件（如 `Table` 只有 PC，`ActionSheet` 只有移动端）
2. 某端不支持某个属性（如 `draggable` 拖拽弹窗只有 PC）
3. 视觉表现不同（`Select` 在 PC 是下拉框，在移动端是底部滚轮）—— 用法相同，表现不同

**禁止的差异**：同名属性在不同端含义不同、同名事件参数结构不同。

## 四、样式与主题方案

### 令牌三层结构

```
第一层  基础色板     --df-blue-1 ~ --df-blue-10     由主色算法推导出的 10 级色阶
第二层  语义令牌     --df-color-primary             指向基础色板中的某一级
                    --df-color-danger
                    --df-color-text-primary
第三层  组件令牌     --df-button-primary-bg         指向语义令牌，允许单独覆盖
```

改主色 → 只改第一层输入值，二三层全部自动跟随。切暗色主题 → 只换第二层的映射关系。

### 小程序端的降级处理

微信小程序基础库 2.9.2+ 支持 CSS 变量，但为兼容低版本与支付宝/字节小程序，`@df-ui/uni` 的样式采用**双轨**：

- SCSS 变量在编译期写死一份默认值（保证任何环境都有样式）
- CSS 变量在运行时覆盖（支持的环境可动态换肤）

### 尺寸单位

| 端 | 单位 | 说明 |
| --- | --- | --- |
| pc | px | 固定像素 |
| h5 | px + `clamp()` | 主体用 px，字号与容器用 clamp 做响应式 |
| uni | rpx | 750 设计稿等分，SCSS 函数 `rpx($px)` 统一换算 |

## 五、构建与发布

| 环节 | 方案 |
| --- | --- |
| 包管理 | pnpm workspace（monorepo，包间用 `workspace:*` 互相引用） |
| 任务编排 | turborepo（增量构建，只重建改动过的包） |
| 库构建 | Vite library mode（pc / h5 / core / tokens） |
| 类型产物 | `vue-tsc --declaration --emitDeclarationOnly` |
| uni 包 | 不构建，源码 + `uni_modules` 规范直接发布 |
| 按需引入 | pc / h5 走 `unplugin-vue-components` resolver；uni 走 easycom 自动 |
| 版本管理 | changesets（自动生成 changelog、统一版本号、批量发包） |
| 文档站 | VitePress + 自定义 demo 容器（代码与预览同源，改组件文档自动更新） |
| 单元测试 | Vitest + @vue/test-utils（pc / h5 / core） |
| 代码规范 | ESLint + Prettier + Stylelint + simple-git-hooks 提交前校验 |

## 六、目录约定

每个组件的标准结构（以 Button 为例）：

```
packages/pc/src/components/button/
├─ index.ts              导出与 install 注册
├─ src/
│  ├─ button.vue         模板与逻辑
│  ├─ button.ts          props / emits 定义（可被 core 与其他端复用）
│  └─ button-group.vue   附属子组件
├─ style/
│  ├─ index.scss         样式入口
│  └─ vars.scss          该组件的组件级令牌
└─ __tests__/
   └─ button.test.ts     单元测试
```

`button.ts` 中的 props 定义**独立于模板**，这样 h5 与 uni 可以直接 import 复用同一份 props 定义，从根本上杜绝三端 API 走偏。

## 七、关键风险与预案

| 风险 | 影响 | 预案 |
| --- | --- | --- |
| 三端 API 走偏 | 用户体验割裂，文档难维护 | props 定义抽到共享文件，CI 加一致性校验脚本 |
| 小程序层级问题 | 弹层被原生组件遮挡 | uni 端弹层统一走 `root-portal` / `cover-view` 方案封装 |
| 小程序无法测量 DOM | 依赖尺寸的组件（Tooltip、虚拟列表）失效 | core 层暴露统一的异步测量接口，各端实现各自适配器 |
| 工作量失控 | 做半年做不完 | 严格分批，第一批 28 个组件先跑通全链路再扩 |
| 主题算法不好看 | 换个主色整套配色崩掉 | 采用 HSL 感知均匀的色阶推导算法，预览页提供实时验证 |
